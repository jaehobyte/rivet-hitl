# 질문 품질 비교 — 모델 정답이 아니라 사람이 판단할 연습 기준

## 초기 과제
> "주문과 결제의 중복을 줄이되 정상적인 재구매는 허용하고 싶습니다."

## Discovery가 발견할 만한 질문 (일부)

| Q-ID | 질문 후보 | 답이 바꾸는 결정 | 대상 / 우선 |
|---|---|---|---|
| Q-001 | 동일한 구매 의도의 반복과 새 구매 의도를 어떤 업무 기준으로 구분하나요? | 중복 주문으로 간주하는 조건·고유성 규칙 | stakeholder / P0 |
| Q-002 | 결제 결과를 확인할 수 없을 때 같은 주문의 새 결제 요청은 어떻게 처리해야 하나요? | 상태 모델·중복 청구 불변조건·실패 테스트 | stakeholder / P0 |
| Q-003 | 기존 결제 실패가 확정된 경우 주문은 유지하나요? | 주문/결제 시도 데이터 관계·재시도 흐름 | stakeholder / P0 또는 P1 |
| Q-004 | PG의 API 이름과 인증 헤더는 무엇인가요? | 외부 기술 사양 | source / 자료로 해결 |
| Q-005 | Redis를 사용할까요? | 기술 선택 | architecture / 현업 인터뷰 제외 |
| Q-006 | 오류 메시지를 파란색으로 할까요? | 핵심 완료 판정과 무관하면 차이 없음 | defer / P2 |

**중요:** 이 표의 질문은 실제 초기 요청에 모두 필수라는 뜻이 아니다. 문제 범위·이미 확인한 자료에 따라 누락 항목과 우선순위가 달라져야 한다.

## 나쁜 질문 → 더 나은 질문

- 유도: "Redis Lock으로 중복 결제를 막아야 하죠?"
  - 개선: "고객이 동일 결제 요청을 거의 동시에 두 번 보내면 어떤 결과를 기대하나요?"
- 넓음: "예외 처리는 전부 어떻게 하나요?"
  - 개선: "결제 PG가 응답하지 않았지만 나중에 성공이 확인된 경우 주문 상태는 어떻게 처리해야 하나요?"
- 의도적 재구매 간과: "같은 고객이 같은 상품을 구매하면 막을까요?"
  - 개선: "같은 상품을 다시 주문했을 때 새 구매와 실수로 반복한 요청을 어떤 업무 기준으로 구분해야 하나요?"

## 인터뷰 답변 뒤 변화 예시

> 답변: "같은 상품이라도 고객이 새로 구매한 것이면 허용하고, 같은 구매 시도가 반복된 것만 기존 주문으로 처리합니다."

인터뷰 후에는 `INTERVIEW_NOTES.md`에 먼저 원문을 추가하고, `SPEC.md`의 '정상 재구매 허용' 업무 규칙을 근거와 연결한다. Q-001은 기본 원칙이 확인되었지만 **새 구매 시도와 기존 시도를 시스템이 구분할 기준**은 아직 미확정일 수 있으므로 `partial`로 남긴다. 다른 Q가 함께 해결되었다면 근거를 적고 닫는다.

## 종료 판단 예시

P0가 모두 확인되거나 남은 P0의 위험을 사람이 명시적으로 수용하고 Must FR·핵심 BR·Hard NFR·검증 기준을 확보했다면, `Q-006`처럼 본질을 바꾸지 않는 미정은 남아도 인터뷰 종료를 권한다.
