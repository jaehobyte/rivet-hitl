# 예제: 기존 주문·결제 아키텍처를 QAS-first로 보강하기

> **학습용 예제.** 앞서 인터뷰로 도출된 주문·결제 상태 정합성 설계의 핵심 개념을 이용하되, 미제공된 코드/API/PG 계약이나 성능 목표를 만들어내지 않는다. 아래 `QAS-`는 이 예제의 ID이며 실제 사용자 요구 ID를 대체하지 않는다.

## 1. Functional/Business Drivers
- 같은 구매 시도의 반복·동시 요청은 주문 하나로 수렴해야 한다.
- 확정 실패 뒤에는 기존 주문에서 재시도가 가능해야 하고 실패 이력을 보존해야 한다.
- `UNKNOWN`에서 동일 주문의 새로운 PG 제출은 허용하지 않는다.
- 성공 증거가 있지만 주문 완료 기록이 유실되면 재결제를 유도하지 않고 기존 주문의 정합성을 복구한다.
- 독립적인 신규 구매의 결제 허용 조건은 아직 업무 정책이 확정되지 않았다고 가정한다. 이를 자동 허용/차단으로 결정하지 않는다.

## 3. 주요 QAS — 6요소

### QAS-R01: 같은 구매 시도의 동시 중복 요청에서 정합성
- **Source**: 고객의 웹/모바일 클라이언트
- **Stimulus**: 동일 `purchaseIntentKey`의 요청이 동시에 여러 번 도착
- **Environment**: 서비스가 정상 동작하고 DB에서 동시 접근 발생
- **Artifact**: 주문 예약 및 결제 시도 저장 경계
- **Response**: 반복 요청을 같은 주문에 연결하고 중복 활성 결제 시도 생성 방지
- **Response Measure**: 같은 키에 대한 N건 동시 요청 테스트에서 저장된 주문 **정확히 1건**, 중복 활성 시도 **0건**. N과 환경은 테스트에서 명시. 외부 PG 청구의 단일성은 별도 검증 전 미입증.
- **확인 상태**: 기존 업무 규칙과 연결된 핵심 불변조건을 예제로 표현

### QAS-R02: PG 응답 유실 시 복구성·정합성
- **Source**: 외부 PG/네트워크
- **Stimulus**: 요청 이후 응답 유실 또는 결과 미확정
- **Environment**: 운영 중 외부 의존 장애
- **Artifact**: 결제 상태 머신, PG 포트, 복구 서비스
- **Response**: `UNKNOWN` 유지, 기존 주문에 대한 새 PG 제출 차단, 객관적인 성공/실패 증거 확인 시에만 상태 전이
- **Response Measure**: 미확정 시나리오 테스트에서 추가 PG 제출 **0회**, 주문이 실패 확정으로 전환되지 않음. PG 증거 조회 가능 여부는 아직 `UNVERIFIED`.
- **확인 상태**: 업무 정책은 확인된 것으로 가정하지만 외부 PG 연동은 미검증

### QAS-M01: 외부 PG 변경의 변경 용이성 (후보)
- **Source**: 운영·개발팀
- **Stimulus**: 결제대행 연동 계약 변경 또는 교체
- **Environment**: 기존 주문·결제 업무를 유지하며 개발
- **Artifact**: PG 인터페이스와 OrderPayment 도메인 서비스
- **Response**: 도메인 정책 변경을 최소화하고 새 PG 어댑터로 교체
- **Response Measure**: 실제 계약이 나오면 변경 파일 수, 핵심 주문 테스트 영향 범위를 기록. 목표 한계는 `TBD`.
- **확인 상태**: 관련 아키텍처 후보이나 공식 NFR로 확정하지 않음

### QAS-P01: 결제 처리 지연 (목표 미정)
- **Source**: 피크 시간 고객 요청
- **Stimulus**: 요청량 증가
- **Environment**: 부하 테스트 환경 (`TBD`)
- **Artifact**: 주문·결제 처리 API
- **Response**: 무결성을 유지하면서 합의된 지연 조건 충족
- **Response Measure**: 목표 p95 및 부하/TPS는 `TBD`; 실제 관측 전 충족 주장 금지
- **확인 상태**: 성능 후보 QAS, 정량 목표 미확정

## 5. QAS → Tactic → Pattern/Module → Test
| QAS | Architectural Tactic | 패턴/모듈 | Trade-off | 실제 검증 경로 |
|---|---|---|---|---|
| R01 | 영속 유일성 + 원자적 활성 시도 예약 | OrderPaymentStore + OrderPaymentService | DB 경합/쓰기 비용 발생 가능 | 같은 키 동시 요청 N건 테스트 |
| R02 | 명시적 UNKNOWN + 외부 결과 재확인 | 상태 머신 + PaymentGatewayPort + ReconciliationService | 결과 확정 지연, 운영 개입 필요 | 응답 유실/재조회 미지원/중복 통지 시나리오 |
| M01 | 도메인/PG 결합 최소화 | Ports & Adapters | 어댑터 관리 비용 | PG Stub 교체 후 회귀 테스트 (실계약 전 제한) |
| P01 | 측정·병목 추적 | DB·API 계측 (필요한 범위) | 추가 계측 비용 | 실제 부하 조건 확정 후 실행 |

## 6. 아키텍처 대안 판단
- A 영속 예약 → PG 호출 → 증거 기반 결과 반영: R01/R02 대응의 근거가 있으며 외부 PG 계약 확인은 추가로 필요.
- B 큐·이벤트 기반: 고부하에서 장점 가능, 큐 중복·운영 복잡도 비용. 요구 TPS가 없으므로 필수로 채택하지 않음.
- C 메모리 Lock 전용: 재시작/다중 인스턴스에 유일성 보장이 없다면 Hard 안전 조건 위반으로 탈락.

**중요:** 이 문서는 실제 프로그램에 대한 테스트 결과가 아니다. 마지막 검증은 실행된 코드·DB·PG 연동 및 실제 부하 실험이 필요하다.
