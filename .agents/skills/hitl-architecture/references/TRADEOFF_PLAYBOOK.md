# Architecture Trade-off / ATAM-lite Playbook

## 평가 순서
1. 관련 Must FR, 핵심 BR, Hard NFR을 만족하지 못하는 후보는 `REJECTED`로 표시한다. 높은 Soft 점수로 상쇄할 수 없다.
2. 나머지 2~3개 대안에 대해 우선 QAS를 어느 tactic으로 충족할지 설명한다. 가정/미확정 외부 계약은 `CONDITIONAL`.
3. `Benefit / Cost / Risk / Evidence / Verification`을 비교한다. **측정 전 성능 우위**나 운영 보장을 확정하지 않는다.
4. 선택한 전략에서 **sensitivity point**(값·방식에 따라 품질이 크게 바뀌는 결정)와 **trade-off point**(두 품질이 동시에 영향을 받는 결정)를 1~3개 식별한다.
5. Risk는 `known / assumption / unverified / policy-blocked / integration-blocked`로 분류하고 회피·검증·사람 승인 조치를 적는다.
6. 중요한 결정 3~5개만 승인 요청한다. 승인된 구조가 환경 변화로 더 이상 QAS를 충족하지 못하면 Architecture로 되돌아간다.

## 결제 시나리오 예시(실제 과제 요구를 대체하지 않음)
- **영속 유일성 + 짧은 트랜잭션**: 동일 구매 키 중복 예약 방지에 유리, 저장소 경합/지연은 검증 필요.
- **큐 기반 순차 처리**: 피크 트래픽의 비동기 분리에는 유리할 수 있으나 큐 중복 전달에 대한 멱등 처리 및 운영 부담 증가. 근거 없는 큐 도입 금지.
- **메모리 Lock만 사용**: 재시작·다중 인스턴스에 안전하지 않으면 Hard 안전 요구 위반 → 탈락.
- **PG Adapter**: 외부 결제 시스템 변경에 유리할 수 있지만, PG 자체의 재조회·멱등 보장을 만들어내지는 못한다.

## 문서에 반드시 남길 출력
| QAS | 선택 tactic/pattern | 혜택 | 비용/다른 품질에 대한 손해 | 미검증 위험 | 검증 계획 |
|---|---|---|---|---|---|

후보를 평가할 때 QAS를 먼저 만들었는지 확인한다. 패턴을 결정해 놓고 이후 QAS를 끼워 맞추면 절차 위반으로 수정한다.
