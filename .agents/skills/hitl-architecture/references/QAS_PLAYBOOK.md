# QAS Playbook — QAW-lite → ADD-lite

이 문서는 실무용 경량화 가이드이며 SEI의 QAW/ADD/ATAM 공식 프로세스를 그대로 구현한 것은 아니다. 품질 시나리오는 요구사항에서 근거를 찾아 생성한다.

## 1. QAS 여섯 요소
1. `Source`: 자극을 발생시키는 주체(고객, PG, 관리 운영자, 네트워크/서버 장애 등).
2. `Stimulus`: 구체적 사건/자극(동시 중복 요청, PG 응답 유실, 급증 트래픽 등).
3. `Environment`: 사건이 일어나는 상태(정상 서비스, 배포 중, 과부하, 복구 중).
4. `Artifact`: 영향을 받는 부분(주문 API, DB, 결제 처리기, 복구 서비스 등).
5. `Response`: 시스템에서 외부 관찰 가능한 기대 반응(새 결제 시도 차단, 상태 보존, 제한 시간 내 조회 등).
6. `Response Measure`: 판정 방법/검증 기준. 수치가 정해졌다면 실제 값; 그렇지 않다면 정확성 불변조건의 검증이나 `TBD + 어떻게 측정할지`.

각 QAS에는 `ID, quality attribute, source evidence, confirmed/candidate/open, importance(H/M/L), difficulty(H/M/L), affected FR/BR`도 추가한다. 사용자 발언 없는 목표 수치나 퍼센트는 만들어내지 않는다. 하나의 QAS가 여러 품질 속성에 기여할 수 있지만 우선 평가할 주 품질을 명시한다.

## 2. QA Inventory 범주
| 품질 속성 | 찾을 업무 영향 | 측정 후보(근거 없는 값은 TBD) | 전형적인 설계 영향 |
|---|---|---|---|
| Reliability / Consistency | 중복 청구·상태 오류 | 위반 건수·불변조건 | 영속 유일성, 조건부 갱신, 멱등 |
| Recoverability / Availability | 장애 중 사용/복구 | 복구 시간, 상태 정합성 | 결과 재확인, 장애 격리, 복구 이력 |
| Performance | 응답 지연, 처리량 | p95·TPS + 부하/환경 | 동기 경로 축소, 인덱스/경합 검토 |
| Scalability | 업무량 증가 | 부하별 처리 능력 | 공유 영속 상태, 수평 확장 고려 |
| Security / Privacy | 부정 접근·개인정보 | 권한별 금지 동작·감사 | 인증/인가, 최소 권한, 데이터 보호 |
| Usability | 고객 혼란/실수 | 태스크 성공, 사용자 행동 | 상태 명료화, 피드백, 복구 안내 |
| Modifiability | API·PG 변경 | 변경 지점·회귀 영향 | 포트/어댑터, 모듈 경계 |
| Testability / Observability | 원인 조사 어려움 | 재현/추적 가능성 | 로그/추적 ID, 테스트 더블 |
| Data/AI specific | 데이터 누수, 결과 불안정 | 분할/지표/재현성 | 입력 검증, 평가 환경 격리 |

범주 목록은 **탐색 체크리스트**다. 모든 속성을 현업에 질문하거나 구현하라는 지시가 아니다. 과제와 무관하면 N/A로 처리한다.

## 3. Hard/Soft 분리와 간이 Utility Tree
- **Hard:** 명시적 불변조건, 금지되는 실패, 법·플랫폼 제약, 명세에서 절대 희생 불가한 품질. Hard 위반 후보는 아키텍처 비교에서 탈락한다.
- **Soft:** 정도의 절충이 가능한 품질(속도, 배포 단순성, 변경 편의 등). 출처가 없다면 `candidate`로 두고 중요도를 가정으로 확정하지 않는다.
- **중요도**: 실패할 때 실제 업무 손실, 요구 범위, Must 여부.
- **난이도/위험**: 현재 코드와 연동 제약, 외부 의존성, 테스트 난이도, 복구 불확실성.
- 우선 순서는 일반적으로 `Hard 위반 위험`, `중요도 H × 난이도 H`, `중요도 H × 난이도 M`, 나머지다. 별도의 합산 숫자 점수를 만들지 않는다.
- `Utility Tree-lite`: 업무목표 → 품질 속성 → 실제 QAS → (중요도, 위험). **표시한 우선순위가 현업 공식 가중치라는 뜻은 아니다.**
- 사람이 가중치를 지정한 경우만 Soft 후보 비교에 가중 합산을 쓸 수 있다. 점수도 관측치가 아닌 분석가의 판단이면 `추정` 표시한다.

## 4. 작성 품질 규칙
**나쁜 예:** `QAS-P01: 빠르게 동작한다. p95 <= 200ms.` (근거 없는 수치)

**좋은 예:** `QAS-P01: 피크 시간대 요청량 증가 → 주문 API의 p95가 합의된 목표를 충족한다; 목표 값/부하 조건은 아직 TBD. 초기 설계에선 성능 검증 계획만 정의.`

**나쁜 예:** `QAS-R01: 고객이 PG 실패한 경우 SAGA 사용.` (솔루션을 요구로 미리 결정)

**좋은 예:** `QAS-R01: PG 응답 유실 시 주문이 실패로 잘못 확정되거나 재청구되지 않아야 하며, 신규 PG 호출 없이 UNKNOWN이 유지된다. 실제 외부 이중 청구 여부는 PG 계약 검증 전 미검증.`

## 5. QAS → Tactics → Pattern → Test
`요구사항/발언 근거 → QAS(6요소) → Hard/Soft 및 중요도/난이도 → tactic → 아키텍처 패턴/모듈 → 반증 가능한 테스트`의 연결을 명시한다.

예: `INT-007/BR-001 → QAS-R01 → 영속 주문 유일성 + 활성 결제 시도 원자적 예약 → 상태 머신/공유 저장소 → 같은 구매 키의 동시 요청 N건에서 주문 1건·중복 활성 시도 0건.`

여기서 해당 검증은 **내부 시스템**에 대한 것이고, 실제 PG가 중복 청구를 막는지는 외부 멱등 계약·통합 테스트가 확보되어야 별도로 입증 가능하다.

## 6. 질문 재라우팅
QAS의 빈칸을 발견했다고 현업에게 무조건 묻지 않는다. `답이 다른 아키텍처와 Must 테스트를 만드는가?` `권한자만 답할 수 있는가?` `자료로 확인할 수 없는가?`에 YES면 인터뷰 질문으로 전환한다. 단순 성능 수치 미확정은 TBD + 측정 계획으로 둘 수 있다.
