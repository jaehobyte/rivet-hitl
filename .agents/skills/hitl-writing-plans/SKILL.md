# HITL Writing Plans — 기술 선택·이유를 포함한 실행 계약

**책임:** `무엇을/왜/어떤 품질로 만들지`는 이미 승인되었다. 이 Skill은 **위임된 기술 스택과 선택 이유, 파일·인터페이스·테스트·구현 순서**를 구체화한다. 실제 구현, 의존성 설치, 프로젝트 생성, 테스트용 제품 코드 작성은 하지 않는다.

**운용:** Spec-Driven Development(SDD) 안에서 고위험 구현 Task의 Test-Driven Development(TDD)를 계획한다. 상세 계약은 `PLAN.md`에, 사람이 판단할 핵심 선택은 짧은 화면 요약에 둔다. 자동 서브에이전트·모델 전환·추가 하네스 설치는 요구하지 않는다.

## 0. 선행 조건 / 자료 우선순위

- Human Gate 2의 범위 승인과 **Human Gate 3의 아키텍처 승인**을 실제 대화·결정 기록에서 확인한다. 없으면 부족한 승인과 `PROPOSED` 상태를 보고하고 계획을 확정하지 않는다. 승인된 같은 범위를 이유 없이 다시 승인받지 않는다.
- **실제 과제 `README.md` 및 제출 규칙** → 승인된 `SPEC.md`, `ARCHITECTURE.md`, `DECISIONS.md` → 현재 코드·테스트·스키마·빌드 설정 순으로 읽는다. 필요한 근거만 `QUESTION_BACKLOG.md`, `INTERVIEW_NOTES.md`에서 확인한다.
- 실제 작업 루트를 확인한다. `workspace/`가 제품 작업 공간이면 그곳을 기준으로 계획하며, 모의시험 도구나 이전 시도의 코드를 현재 제품으로 취급하지 않는다.
- 공식 Must/제출 규칙 > 사용자가 실제 승인한 범위·정책 > 확인된 인터뷰·SPEC > 설계 가정 순으로 판단한다. Must 동작을 바꾸는 충돌은 보고하고 해당 결정을 멈춘다.
- Hard Constraints, 상위 QAS, 선택한 tactics, 모듈·상태·트랜잭션 경계와 미검증 운영 정책을 보존한다. 기술 선정 권한이 아키텍처나 업무 정책을 다시 정할 권한은 아니다.

## 1. 범위·구현 가능성 스캔

1. **Repo reality check:** 기존 시작·테스트 명령, 배포/브라우저 연결, 모듈·함수, 제출 파일을 조사한다. 존재하는 파일과 앞으로 생성할 파일을 구분한다.
2. **Must-first:** Must와 Hard NFR부터 계획한다. Should는 Must를 구현하는 데 필요한 부분만 포함하고, 나머지는 별도 후보로 둔다. Out은 구현하지 않는다.
3. **Blocking ledger:** 다음을 구분하고 영향을 받는 Task만 연결한다.
   - `Policy Blocker`: 업무 규칙 미정. Must의 기대 동작이 달라지면 해당 Task는 `BLOCKED`; 정책을 창작하지 않는다.
   - `Integration Blocker`: 실제 계약·데이터 없음. 승인된 mock/추상 계약의 내부 검증과 실제 통합 검증을 분리한다.
   - `Architecture Assumption`: 검증할 기술 가정. 확인 방법, 담당 Task, 실패 시 재검토할 결정을 적는다.
   - `QAS Gap`: 측정 목표 미정. 측정 계획과 한계를 남기며 임의 목표나 PASS를 만들지 않는다.
4. **실행 순서:** 확인된 잔여 시간과 의존성을 고려해 끝까지 동작하는 최소 Must 흐름을 먼저 정한다. 웹 과제는 첫 핵심 흐름에 최소 화면→API→판정/저장→관측을 연결한다. 시간 정보가 없으면 미확인으로 두며 임의의 잔여 시간을 쓰지 않는다.

## 1.5. 실행 기술 스택 선정 — File Map 작성 전

### A. 선택 권한

- 기존 프로젝트의 스택과 승인된 Architecture의 기술을 먼저 유지한다. 단순한 취향이나 익숙함으로 교체하지 않는다.
- Architecture에서 미정으로 남기고 계획 단계에 위임한 항목만 선정한다. 위임 여부가 불명확하면 선정안을 제시하되 승인된 것으로 쓰지 않는다.
- 언어·런타임, 서버, UI, 저장소/드라이버, 테스트·브라우저 도구 중 필요한 영역만 다룬다. 특정 제품을 모든 과제의 기본값으로 고정하지 않는다.
- 선택이 **배포 구조, 데이터 소유·트랜잭션 경계, 인증·권한, 외부 호환성 또는 Hard QAS**를 바꾸면 해당 선택을 `Human Gate 3 재검토`로 보낸다. 같은 구조 안의 위임된 선택은 Gate 4에서 PLAN과 함께 승인받는다.

### B. 환경 확인과 선정

- 파일·설정·잠금 파일을 읽고, 버전·기능 존재 조회 같은 부작용 없는 명령으로 현재 환경을 확인한다. 설치, 서버 기동, 제품/테스트 코드 작성은 여기서 수행하지 않는다.
- 버전은 실제 조회값·잠금 파일 근거와 제안값을 구분한다. 모르면 `버전 PENDING`으로 쓰고 숫자를 만들지 않는다. 설치됨은 제품 호환성·성능·보안 검증 완료를 뜻하지 않는다.
- 제품 코드가 없더라도 환경에서 확인할 수 있는 정보로 선정안을 먼저 작성한다. 스택 선택 전체를 Implementation의 T-00으로 떠넘기지 않는다.
- 확인할 수 없는 항목만 `PENDING`으로 남긴다. 각 항목에 **확인 방법·최초 확인 Task·실패 시 처리**를 붙인다. 선택을 좌우하는 사실 자체가 없으면 영향받는 계약을 보류하고, 제안과 확정 계약을 섞지 않는다.
- **선정 기준:** 과제 제약과 승인된 FR/BR/QAS 충족 가능성 → 기존 환경 재사용 → 설치·구현·운영 부담 → 테스트 가능성과 사람의 설명 가능성. 설치가 쉽다는 이유로 필수 무결성·보안을 생략하지 않는다.
- 실제 인증/외부 계약이 없으면 연습용 대체안을 별도로 제안할 수 있으나, 승인 없이 실제 계약을 대체하거나 운영 보안 충족으로 취급하지 않는다.

### C. PLAN에 남길 기술 선택 표

`File Map` 앞에 아래 **표 하나**를 작성한다. 새로운 기술 비교 문서는 만들지 않는다.

| 영역 | 선정안·버전 | 이번 과제에서 선택한 이유 | 한계·미확인 사항 | 환경 확인 상태 |
|---|---|---|---|---|

- 각 선택 이유는 **요구사항/QAS/환경 근거 → 이 선택이 필요한 이유**를 1문장으로 설명한다. “유명해서”, “가볍고 빠르다” 같은 일반 소개로 끝내지 않는다.
- 핵심 선택에만 유력한 대안 1개와 채택하지 않은 이유를 같은 행에 짧게 덧붙인다. 모든 라이브러리를 비교하지 않는다.
- 환경 확인 상태에는 `확인됨(명령·관측)` / `일부 확인(공백)` / `PENDING(확인 방법·Task)`를 적는다. 민감한 키·토큰은 기록하지 않는다.
- **선정안, 환경 확인, 승인 상태, 기능 검증은 서로 다르다.** 승인 상태는 PLAN의 현재 상태·Gate 기록으로 관리하고, 기능 검증 결과는 실행 전에는 모두 `NOT RUN`이다.

설명 방식 예시: “여러 기록의 전체 반영·전체 취소 요구 때문에 트랜잭션 저장소를 선정한다. 현재 배포 구조에 맞는 제품을 제안하되, 저장 중 실패와 재시작 시의 보장은 실행 시험으로 확인한다.” 제품명만으로 보장을 단정하지 않는다.

## 2. 파일 구조를 Task보다 먼저 결정

- **File Map:** 기술 선정안에 맞춰 생성/수정/테스트할 경로와 파일별 책임을 정한다. `기존 확인`과 `생성 예정`을 구분하고 경로의 기준 디렉터리를 명시한다.
- **Interface Contracts:** Task 간 공유 함수·인자/반환 타입, API 요청·응답, 상태·오류, 영속성 경계를 구체화한다. 기존 계약은 실제 코드 근거를, 신규 계약은 `PROPOSED`임을 표시한다. 세부 지역 함수는 구현자에게 맡긴다.
- 공유 계약이 위임된 기술 선택이면 여기서 제안한다. 업무 정책 또는 중요한 구조를 바꾸면 해당 Gate로 돌린다. 새 함수를 제안하는 것과 이미 존재한다고 주장하는 것을 구분한다.
- 시작·테스트·빌드 명령은 현재 존재하는 명령과 구현 단계에서 만들 스크립트를 구분한다. 새 스크립트는 소유 Task와 생성할 설정 파일을 연결한다. 미실행 명령을 실행 가능한 것으로 검증했다고 쓰지 않는다.
- 아직 결정할 수 없는 경로·계약은 확인 행동과 의존성을 명시한다. 나머지 승인 범위의 계획까지 일괄 중단하지 않는다.

## 3. FR/BR/AC/QAS → Task → Test 매핑

- 이번 범위의 **모든 Must FR/BR/AC와 우선 QAS**를 하나 이상의 Task 및 검증 방법에 연결한다. 빈 연결은 `GAP`이다. 근거 문장의 전체 내용을 반복 복사하지 않는다.
- 기존 ID를 유지한다. AC ID가 없으면 원문 위치와 연결한 안정적인 참조 별칭임을 명시하며, SPEC이 이미 부여한 ID처럼 쓰지 않는다.
- `Unit / Integration / Browser / Restart / Concurrency / Load / Security / Manual` 검증 레벨을 지정한다. 단위 테스트 통과로 운영 품질 전체를 입증할 수 있다고 계획하지 않는다.
- **Review Focus:** 명세의 공백 때문에 실패할 가능성이 높은 예외 3~5개를 골라 실패 입력·기대 결과·소유 Task·테스트 이름을 적는다. 미정 정책은 질문/차단 항목으로 남기고 임의의 기대값을 만들지 않는다.
- 외부 계약·실데이터·정책이 없어 수행할 수 없는 검증은 `PENDING / NOT TESTABLE`로 분리한다. 허용된 내부 테스트까지 불가능한 것으로 뭉뚱그리지 않는다.

## 4. Task 크기와 TDD 실행 명세

**하나의 Task = 독립적으로 관찰 가능한 결과물 + 자기 테스트 사이클 + 리뷰·거절 가능한 단위.** 단순 디렉터리 생성·설정은 관련 기능 Task에 흡수한다. 별도 T-00이 필요하면 남은 환경·호환성 확인만 맡기며, 이미 할 수 있었던 스택 선정과 이유 설명을 미루지 않는다.

```markdown
### Task T-01: [사용자가 관찰할 결과 중심 제목]
- Priority / depends_on: Must / 선행 Task 또는 없음
- Covers: FR-..., BR-..., AC-..., QAS-...
- Files: Create ..., Modify ..., Test ... (작업 루트 기준)
- Consumes / Produces: 공유 계약·타입·상태·오류
- RED: 테스트 이름·대표 입력·assert·실행 명령·기대 실패 원인
- GREEN: 최소 코드의 역할·위치 (구현 본문은 작성하지 않음)
- REFACTOR: 계약을 유지하는 정리; 필요할 때만
- Verify: 실행 명령·기대 결과·회귀 범위·QAS 실측/수동 확인
- Exit: 관찰 가능한 완료 조건·증거; commit은 허용 환경에서만
```

- RED는 의도한 기능의 부재/결함 때문에 실패해야 한다. 도구 누락·문법 오류·외부 서버 미가동은 기능 RED가 아니다. 재현 불가 시 구현자가 `RED_NOT_RUN(reason)`을 남기도록 계획한다.
- GREEN과 리팩터링 후 통과는 **Implementation에서 실제 실행한 증거**로만 인정한다. 이 Skill은 실행 절차와 기대 결과를 적을 뿐 RED/GREEN을 수행했다고 기록하지 않는다.
- 고위험 상태 전이·동시성·원자성·복구에는 정상 및 반례 테스트를 함께 둔다. 관련 회귀와 최종 전체 테스트·빌드·정적 검사를 각각 계획하고, 없는 검사 도구는 현재 한계 또는 도입안으로 구분한다.
- 문서·탐색·단순 표시처럼 TDD가 맞지 않는 작업은 `NON_TDD`와 이유·실제 확인 방법을 적는다. UI에도 핵심 업무 규칙이 있으면 그 동작을 검증하며 UI 전체를 면제하지 않는다.
- Git commit은 허용된 저장소에서만 수행하도록 계획한다. Git Push·외부 전송·도구 제한은 해당 과제 규칙을 따른다.

## 5. PLAN.md 작성·Self-Review

실제 작업 루트의 **`PLAN.md` 하나만** 작성하거나 안전하게 갱신한다. SPEC·Architecture를 다시 복사하거나 별도 요약/기술 보고서를 만들지 않는다. 문서 첫머리에 현재 상태를, 끝에는 기존 실행·승인 이력을 보존한다.

```markdown
# Implementation Plan — [과제]
- Current Status: PROPOSED — Human Gate 4 승인 대기
- Gate 2 / Gate 3: 승인 범위와 실제 근거
- Plan revision / approval: 이번 개정 및 승인 근거; 없으면 PENDING
- Source: README.md / SPEC.md / ARCHITECTURE.md / DECISIONS.md
- Goal / Architecture / Available time: 목표·승인된 구조·확인된 시간
- Global Constraints: 과제의 명시적 제약

## 사람용 계획 요약
[먼저 만들 것 / 사용 기술 / 선택 이유 / 한계·차단 / 확인 방법 — 5줄]

## 기술 선택
[1.5절의 표: 선정안·이유·한계·환경 확인]

## File Map & Interfaces
[작업 루트 기준 경로·책임·공유 계약·명령]

## Requirement & QAS Coverage / Review Focus
[ID → Task → Test/검증 레벨; 주요 실패 입력과 기대 결과]

## Tasks
[T-01 ... RED → GREEN → REFACTOR → Verify]

## Pending / Excluded / Integration Limits
[영향 Task·확인 방법·실패 시 처리]

## 실행·변경 이력
[기존 실제 기록 보존; 계획 작성 중에는 실행 결과를 채우지 않음]
```

- **현재 상태와 과거 기록을 분리한다.** 과거의 `미승인/미실행`을 현재 판정처럼 남기지 말고 시점·대체 근거를 명시한다. 실제 승인·실행 원문은 삭제하거나 새로 만들어내지 않는다.
- 재계획 시 기존 승인을 조용히 취소하거나 확대하지 않는다. 바뀐 기술·계약·Task와 필요한 재승인만 표시한다. 실제 승인 사실이 모호하면 그 부분만 사람에게 확인한다.

자체 검토:

- [ ] 기술 선택이 File Map보다 먼저 있으며, 기존/승인된 기술을 존중했는가?
- [ ] 선택 이유·주요 한계·환경 확인 상태가 있고, 선정·설치·승인·기능 검증을 구분했는가?
- [ ] 모든 Must와 우선 QAS가 Task·검증에 연결됐으며, 남은 GAP의 영향이 드러나는가?
- [ ] 공유 타입·함수명·상태·오류와 제안 시작/테스트 명령이 일치하는가?
- [ ] RED의 대표 입력·assert·실패 이유와 GREEN 이후 회귀가 구체적인가?
- [ ] 첫 핵심 흐름을 사람이 일찍 관찰할 수 있고, 불필요한 기능·문서 복제가 없는가?
- [ ] 현재 승인 상태가 일관되고, 미정 정책·버전·QAS 목표·실행 결과를 창작하지 않았는가?

## 6. Human Gate 4 — 사람이 이해하고 승인하는 인계

PLAN을 저장한 뒤 터미널에는 아래 **5줄을 기본 보고 형식**으로 쓴다. 긴 ID 목록과 파일별 상세는 문서에 남긴다.

1. **먼저 만들 것:** 첫 사용자 흐름과 뒤에 확장할 순서.
2. **사용 기술:** 핵심 기술 조합과 유지/신규 선정 구분.
3. **선택 이유:** 중요한 이유 최대 3개를 업무 요구와 연결.
4. **한계·차단:** 감수하는 비용, 미확인 환경, 승인할 선택과 막힌 범위.
5. **확인 방법:** 대표 성공·실패 시험과 사람이 확인할 동작.

- **사용자의 명시적 승인 전에는 구현을 시작하지 않는다.** 위임된 기술 선택과 PLAN은 Gate 4에서 함께 검토한다. 승인된 구조를 바꾸는 선택만 Gate 3로 돌린다.
- 사용자가 수정하면 PLAN을 고치고 재검토한다. 승인하면 현재 상태·승인 범위·근거를 갱신한다. 사람의 승인이 없는 기술을 “확정”으로 바꾸지 않는다.
- 이해 확인이 필요하면 핵심 선택 하나의 이유나 예상 동작을 짧게 확인한다. 별도 긴 퀴즈나 새 승인 단계를 만들지 않는다.
- 사람이 구현을 지시하면 `$hitl-implementation`이 승인된 PLAN을 읽어 수행한다. **본 Skill은 자동으로 다음 Skill을 호출하거나 서브에이전트를 생성하지 않는다.**
- `FAST`에서는 비교 대안·중복 설명·Should 계획을 줄인다. Must/Hard를 임의 삭제하지 않으며 기술 선택 이유·검증 계약·미실행 표시·승인 경계는 유지한다.
