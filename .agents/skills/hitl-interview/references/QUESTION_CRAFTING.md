# Question Crafting Playbook — Discovery / Interview 공용 참고

이 문서는 **질문 작성이 필요한 경우에만** 읽는다. 목록은 검토용 탐색 지도일 뿐, 모든 항목을 현업에 물으라는 뜻이 아니다.

## A. 먼저 질문 필요성 판단 — Question Opportunity

1. **근거 탐색**: README, 코드, 명세, 데이터, 이미 받은 INT 발언으로 답이 있는가? 있으면 새 질문 금지, 근거를 적고 해결.
2. **결정 차이(Decision Delta)**: 답변 A와 B가 실제로 다른 `핵심 FR/BR/Hard NFR/ARCH/AC`를 만들까? 두 답이 동일 구현·테스트를 낳으면 현업에 질문하지 않는다.
3. **권한 확인**: 업무 정책인가(현업), 범위·위험 수용인가(사람), 기술 수단인가(설계자), 자료 사실인가(파일)? 현업이 답할 일만 현업으로 보낸다.
4. **영향과 불확실성**: 높은 실패 비용·되돌리기 어려움·미확정의 조합부터 순위 부여. 의사결정 영향이 큰 P0는 최우선, P1은 시간과 위험에 따라, P2는 유예.
5. **의존 관계**: 목적·용어 → 정상 흐름 → 정책 경계 → 실패·동시성 → 품질 목표 → 수용 확인 순으로, 선행 답으로 해결되는 후행 질문은 묻지 않는다.
6. **질문 비용**: 같은 결정을 묻는 중복 질문은 합치고, 한번에 여러 정책이 섞인 질문은 분리한다. 질문이 매우 넓다면 구체적인 한 흐름의 사례로 좁힌다.

필드 권장: `Q-ID`, `열린 질문`, `답에 따라 바뀌는 A/B 결정`, `관련 FR/BR/NFR/ARCH/AC`, `근거`, `질문 대상`, `P0/P1/P2`, `상태`, `연관 INT-ID`.

## B. 질문 작성 패턴 — 7가지

1. **Goal / Why**: '이 과정에서 해결하고 싶은 가장 큰 업무 실패는 무엇인가요?' — 요구 목적 자체 불명확할 때.
2. **As-Is vs To-Be**: '현재는 이 상황을 어떻게 처리하고, 개선 뒤에는 무엇이 달라져야 하나요?' — 개선 대상의 실제 흐름 부족할 때.
3. **Actor & Authority**: '이 정책은 누가 결정하며, 고객/운영자/관리자별 기대가 다른가요?' — 역할/권한 불명확할 때.
4. **Happy Path / Event**: '이 일이 시작되는 조건과 성공으로 끝났다는 신호는 무엇인가요?' — 핵심 경로 불명확할 때.
5. **Boundary / Counterexample**: '동일 상품을 다시 산 경우처럼 겉으로 같지만 다른 요청은 어떻게 판단하나요?' — 중복/정체성 경계에 결정 필요할 때.
6. **Failure / Race / Recovery**: '결과가 확인되지 않는 상태에서 같은 요청이 동시에 들어오면 어떤 결과가 반드시 지켜져야 하나요?' — 불변조건·실패 정책 불명확할 때.
7. **Playback / Falsification**: '제가 이해한 [정책]이 [경계 사례]에도 동일하게 적용되나요?' — 정책을 요약 검증할 때.

### 열린 질문과 확인 질문의 순서
- 아직 의도가 불명확하면 열린 질문부터. 선택지나 기술 해법을 선제 제시하지 않는다.
- 이미 구체적 정책을 설명받았다면 좁고 반증 가능한 확인 질문을 사용한다. 같은 사실을 반복 질문하지 않는다.
- 높은 위험의 예외에는 한 가지 구체적 사건을 제시하되, 답을 암시하지 않는다.
- 답변이 '모르겠다/담당 아님'이면 정책을 상상하지 말고 권한자 확인·범위 조정·가정 위험 승인으로 라우팅한다.

## C. 질문 교정: 실행 전 8문항 자체 점검

- [ ] 앞선 자료에 이미 답이 있는가? 있다면 삭제.
- [ ] 현업이 답할 업무 결정인가? 기술 스택을 묻고 있지 않은가?
- [ ] 이 답이 달라지면 무엇을 바꾸는지 구체적일까?
- [ ] 'Redis/Queue/마이크로서비스를 쓰면 될까요?'처럼 해결책을 유도하지 않는가?
- [ ] 'A, B, C, D를 어떻게 할까요?'처럼 여러 독립 질문을 묶지 않았는가?
- [ ] '안전하게/빠르게/일관되게'를 평가 가능한 행동·측정으로 바꾸었는가?
- [ ] 비슷한 질문과 합치거나 이미 답한 질문을 제거했는가?
- [ ] 사용자가 복사해 현업 담당자에게 그대로 보낼 수 있는 한 문장인가?

## D. 커버리지 점검 (Clear / Partial / Missing / N/A)

- **목표**: 누구의 어떤 업무 문제가 어떻게 해결되는가?
- **범위**: Must / Out / 성공 조건 / 필수 제출물.
- **정체성·데이터**: 고유 키, 중복의 정의, 데이터 관계, 저장·보존.
- **상태·정책**: 정상 전이, 금지 전이, 권한, 일관성/불변조건.
- **예외·복구**: 실패, 타임아웃, 재시도, 중복 이벤트, 경합, 장애 복구.
- **외부 의존**: 연동 주체, 약속된 입력·출력, 확인할 수 없는 결과.
- **중요 NFR**: 안전/신뢰/정확성/성능/보안/변경 용이성 중 이번 과제의 Architecture Driver만.
- **수용 조건**: 어떤 입력에서 무엇을 관찰해야 PASS인가?
- **데이터·AI형**: 타깃/레이블/평가 지표, 분할, 누수, Baseline, 재현성.

이 매트릭스는 **발견을 돕는 체크리스트**다. 빠진 범주를 이유 없이 모두 질문으로 바꾸지 말라. 특정 과제에 해당 없는 범주는 N/A로 마감한다.

## E. 우선순위 예시 (결제 과제)

- **P0 / Stakeholder:** '결제 결과가 미확정인 동일 주문에 재결제 요청이 오면 어떻게 처리해야 하나요?' → 차단 여부, UNKNOWN 상태/검증 테스트.
- **P0 / Stakeholder:** '같은 구매 의도의 반복과 새로운 구매 의도를 어떻게 구분해야 하나요?' → 주문 생성의 정체성 규칙·중복 정책.
- **P1 / Stakeholder:** '결제 결과가 계속 미확정이면 운영자가 언제 어떤 조치를 해야 하나요?' → 복구 시나리오(핵심 범위일 경우 P0).
- **Technical / No interview:** 'Idempotency를 Redis로 구현할까요?' → 설계·코드 검토로 해결.
- **Deferred / No interview:** '에러 메시지 색은 무엇으로 할까요?' → 필수 수용조건이 아니라면 생략.

## F. 인터뷰 종료 규칙

P0가 해소되었거나 사람이 잔여 위험을 명시적으로 수용했고, Must FR·핵심 BR·Hard NFR·핵심 정상/실패 시나리오·AC가 설명되면 종료를 제안한다. P1/P2의 해소를 강제하지 않는다. 수치로 산출한 '모호성 점수'는 추정 지표일 뿐 강제 승인 조건으로 쓰지 않는다.
