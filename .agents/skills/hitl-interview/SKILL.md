# HITL Interview (실무자 인터뷰 근거 추적과 다음 질문 설계)

## 핵심 원칙
- Codex는 **질문 설계·기록·해석**을 한다. 사람만 별도의 현업 담당자 에이전트에게 실제로 인터뷰한다.
- 새 답변이 전달되면 **원문 보존이 분석보다 먼저**다. 모델이 알아서 인터뷰 사실/발언자/시간을 꾸미면 실패.
- 목표는 모든 질문을 소진하는 것이 아니라 **핵심 동작·설계·평가를 바꾸는 모호성을 충분히 해소하는 것**이다.

## 인터뷰 입력을 받았을 때 — 아래 순서 고정
1. **Append-first**: `INTERVIEW_NOTES.md` 파일이 없으면 생성. 실제 질문과 답변을 편집하지 않고 `INT-001`부터 순차 추가. 출처(사용자가 붙여 넣은 텍스트 / 허용된 실제 파일), 화자/시간(알 때만), 대응 Q-ID를 기록. 기존 원문은 삭제·덮어쓰기 금지. 일부 정보만 받으면 제공받은 그대로 기록하고 부족한 부분은 `미제공`으로 표기. 원문 뒤 `Codex 해석` 별도 섹션 작성.
2. **Atomic Claims**: 답변을 하나의 정책/조건/예외/제약 단위로 쪼개어 각각 `confirmed/tentative/unresolved` 표시. 현업이 공식 결정권자인지 확실하지 않으면 `needs_authority_check`, 오해 위험이 있으면 `needs_confirmation`으로 둔다.
3. **Backlog reconcile**: 해당 질문과 **함께 해결된 연관 질문**을 `answered/partial/deferred/needs_confirmation`으로 수정하고 `INT-ID`를 연결. 새 용어, 반례, 상충 정책, 핵심 예외가 나오면 Q-ID를 추가. 답변에서 이미 해결된 질문은 다시 추천하지 않는다.
4. **SPEC update**: `SPEC.md`의 FR/BR/NFR/CON, 범위, 전제/후행 상태, 성공 기준을 근거 링크와 함께 갱신한다. 원문에 없는 수치, 시간·규정, 목표 TPS를 확정하지 않는다.
5. **Scenarios**: 중요 Use Case 정상 흐름과 대안/실패/타임아웃/중복/경합/복구 중 관련되는 것만 점검하고, 결정에 필요한 공백은 질문 후보로 만든다. 모든 경우의 수를 상상해 범위를 늘리지 않는다.
6. **Question Gate**: `references/QUESTION_CRAFTING.md`를 읽고, 각 후보에 대해 두 개의 실질적으로 다른 가능한 답을 가정했을 때 `FR/BR/ARCH/NFR/AC` 중 무엇이 어떻게 달라지는지 적는다. **같은 결과면 묻지 않는다**. 자료로 해결되거나 기술 선택이면 적절한 대상에 넘긴다.
7. **Question Form**: 기본은 현업의 언어로 작성한 **열린 질문 한 문장**. 선행 답을 확인해야 할 때만 닫힌 확인 질문. 적합하면 반례·경계 사건을 하나 제시하지만 답변을 유도하지 않는다. 질문의 이유는 참가자에게만 부연하고 페르소나에게 보내는 질문 자체는 간결하게 만든다.
8. **Deliver**: 현업 담당자에게 복사할 **다음 질문 1개**(Q-ID, 질문, 구체적 Decision Delta), P0 잔여 수, 해소된 결정, `SPEC.md` 변경 요약만 화면에 출력. 모든 후보를 메시지에 반복 나열하지 않고 `QUESTION_BACKLOG.md`에서 관리한다.

## 질문 유형 전환: 이미 확보된 사실에 따라 다르게
- 문제를 아직 모르면: **목적 / 업무 실패** 질문.
- 정상 흐름이 흐리면: **트리거 / 핵심 경로 / 완료 상태** 질문.
- 비슷한 사건이 다른 결과를 가져야 하면: **정의 / 구분 기준 / 반례** 질문.
- 상태·안전성이 중요하면: **실패 / 중복 / 동시성 / 복구** 질문.
- NFR이 설계를 좌우하면: **측정 조건 / 최소 허용 수준 / 우선순위** 질문.
- 정책을 이미 들었다면: **정확한 해석 재확인 / 충돌 확인** 질문.
- 위 질문으로 바뀔 결정이 없으면: **추가 질문 불필요**.

## 강력한 필터 (반드시 적용)
- `FR`: 핵심 기능의 외부 관찰 가능한 동작·입력·출력이 바뀌는가?
- `BR`: 업무 정책·금지 전이·불변조건이 바뀌는가?
- `ARCH`: 데이터 소유/키/상태/모듈 경계·트랜잭션·연동 계약이 바뀌는가?
- `NFR`: 중요한 품질 제약이나 측정 가능한 목표가 바뀌는가?
- `AC`: 중요한 수용 테스트의 기대값/입력이 바뀌는가?

위 다섯 항목 모두 **NO**면 `deferred`하고 추가 질문하지 않는다. YES여도 기존 자료에서 해결하거나 기술자가 결정할 수 있으면 현업에 묻지 않는다. P0가 아니라면 남은 시간과 재작업 위험을 고려해 유예할 수 있다.

## 입장을 흔들어 보는 후속 질문(필요할 때만)
- 현업이 제안한 구체 기술이 진짜 업무 필요인지 분리한다. **솔루션 유도 대신 결과**를 되묻는다.
- 답변이 기존 INT/README와 충돌하면 어느 쪽을 공식 정책으로 볼지 확인한다. 조용히 마지막 답변으로 덮어쓰지 않는다.
- 같은 단어를 다른 의미로 쓴다면 도메인 용어 정의를 확인한다. 예: 주문 재시도 ≠ 결제 재시도.
- 예외 질문은 성공 경로에서 발생 가능한 진짜 실패를 묻고 가정적·무한한 엣지케이스 생성은 하지 않는다.

## NFR / QAS 정보가 실제로 추가되었을 때
- 응답시간, 사용 가능성, 보안 권한, 안전성, 복구 시간, 변경 빈도 등 **측정 가능한 품질 요구**가 인터뷰에서 나오면 원문과 함께 `SPEC.md`의 **품질 속성 후보 / 근거 / 측정조건**을 갱신한다.
- QAS 6요소 가운데 **Stimulus·Environment·Response·Response Measure**가 업무적으로 중요하지만 미정이면 후속 질문 후보로 분류한다. 모든 빈칸을 현업에 묻지 않는다.
- 질문은 `답변이 Must FR/BR/Hard NFR/핵심 QAS 또는 구조 선택을 실제 바꾸는지`로 필터링한다. 예: '일반적인 피크 시간은 언제인가?'는 트래픽 설계에 영향이 있을 때만 묻고, '목표 p95는?'은 근거가 없으면 임의 확정 대신 측정 계획으로 유예할 수 있다.
- `Policy Blocker / Integration Blocker / Architecture Assumption / QAS Gap`을 구분한다. 실제 코드·PG 계약의 부재가 **개념 설계 전체의 자동 중단**을 뜻하지 않는다.
- Human Gate 2에서 구현할 Must/Should/Out, 사람만 승인할 위험, 핵심 품질 속성 후보를 함께 보여준다. 인터뷰 후 Architecture가 직접 QAS 우선순위를 결정하되 사용자 승인을 기다린다.


## 인터뷰 종료
P0가 모두 해결됐거나 미해결 P0 위험을 **사람이 명시적으로 수용**하고, Must FR·핵심 BR·Hard NFR·중요 정상/실패 흐름·AC를 설명할 수 있으면 **추가 인터뷰 종료를 권고**한다. 남은 P1/P2는 이유와 담당자를 기록한다. 사람의 범위 확정 이전에 Architecture로 자동 이동하지 않는다.
