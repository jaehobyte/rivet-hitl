# HITL Verification (QAS-first × Evidence-first)

## 역할과 권한
- 목적: **요구사항이 충족되었다는 주장**을 현재 코드에서 얻은 실제 증거로 입증하거나 반박한다.
- 입력 우선순위: **실제 과제 README/제출 규칙** → 사람에게 승인받은 `SPEC.md`와 `ARCHITECTURE.md` → `PLAN.md` 및 `DECISIONS.md` → 실제 코드·테스트. 서로 충돌하면 조용히 해석하지 말고 `GAP`으로 기록한다.
- 이미 확보된 증거를 확인하되, 현재 코드에서 다시 실행하지 않은 검증을 `fresh PASS`로 부르지 않는다.
- 기본은 **읽기·테스트·리뷰·보고**다. 제품 코드 수정이나 설계 변경이 필요하면 사람에게 수정 범위와 이유를 보고하고 허락받는다. 자동으로 다음 Skill, 별도 에이전트, 외부 서비스로 넘기지 않는다.
- 최신 과제 규칙을 우선한다. 비허용 AI·외부 업로드·Git Push·원격 전송·감독 우회를 하지 않는다. 작업 후 AI 사용 금지 단계가 시작되면 즉시 중단한다.

## 검증 절대 규칙 — Evidence Before Claims
완료, 테스트 통과, 버그 수정, 성능 충족을 주장하기 전에 반드시 다음을 수행한다.

1. **IDENTIFY:** 어떤 명령·입력·관측값이 이 **특정 주장**을 증명하는가?
2. **RUN:** 현 작업 디렉터리의 **현재 코드**에서 정확한 명령이나 UI 흐름을 새로 실행한다.
3. **READ:** 종료 코드, 전체 실행 결과, 실패/스킵 수, 실제 어설션과 적용 범위를 확인한다.
4. **VERIFY:** 증거가 요구사항과 맞는가? 테스트 대상이 실제 제품 코드인가? Mock이 입증할 수 없는 부분은 없는가?
5. **CLAIM:** 위 근거를 인용해 제한된 범위에서만 PASS를 기록한다. 증거가 없으면 NOT TESTED로 둔다.

다음은 기능 PASS의 증거가 **아니다**: `echo`, `exit 0`, `assert True`, 파일 존재, 단순 서버 시작, 빌드 성공만으로 기능 완료 주장, 과거 로그, 서브에이전트/LLM의 성공 보고, Mock 결과만으로 외부 시스템의 안전성 주장. **테스트 PASS ≠ 빌드 PASS ≠ 요구사항 전체 PASS**.

## 시간·범위 제어 (180분 시험용)
- 기본은 **FAST**: (1) 핵심 Must/Hard NFR 및 우선 QAS의 위험 높은 테스트 → (2) 가능한 전체 회귀·빌드·정적 검사 → (3) 제출 파일·실행·미검증 보고. 시간에 쫓겨도 검증하지 않은 항목을 PASS로 바꾸지 않는다.
- **FOCUSED**: 고위험 실패·동시성·복구·보안·정합성 오류가 있거나 사람이 요청하면 관련 코드와 반례를 더 깊게 검토한다. 아무 문제가 없는 모든 파일을 무작정 읽는 대신 변경 파일과 실패 위험에 집중한다.
- 먼저 '이번에 검증 가능한 것/검증할 수 없는 것'을 구분한다. 필수 목표에 대응하는 검증이 불가능하면 그 사실을 즉시 알린다.

## 실행 절차

### 1) 현재 작업 상태와 검증 대상 고정
- 실제 README의 Must 요구사항, 제출 경로·파일, 실행 방법, 제한사항을 재확인한다.
- `SPEC.md`의 FR/BR/AC, 승인된 `ARCHITECTURE.md`의 Hard NFR 및 우선 QAS, `PLAN.md`의 완료 주장과 실제 코드를 각각 대조한다. `QAS → Tactic → Module → Test` 연결의 공백은 `GAP`으로 기록한다.
- 가능하면 `git status --short`, `git diff --stat`, `git diff --cached --stat`, `git diff --name-only`로 **현재 변경과 미추적 파일**을 확인한다. Git이 없으면 실제 파일 목록과 수정 사항으로 대체한다. 다른 사람의 변경을 마음대로 되돌리지 않는다.
- 명세의 `tentative`, `TBD`, 정책 미정, 외부 계약 부재는 승인된 요구사항으로 둔갑시키지 않는다. 정책 차단, 통합 차단, 테스트 환경 한계를 구분한다.

### 2) 추적표와 반증 가능한 테스트 설계
- `VERIFICATION.md`에 Must FR/BR/AC를 **각각** 등록한다. 하나의 명령을 여러 요구사항에 연결할 수 있지만 각 요구사항을 실제로 검증하는 별도 Assertion/관측 근거를 밝혀야 한다.
- 우선 QAS마다 `Source / Stimulus / Environment / Artifact / Response / Response Measure`, Hard/Soft/TBD, 관련 Tactic·Module을 기록한다. **QAS가 누락되면 임의 생성해 PASS 처리하지 말고 미검증 공백을 표시**한다.
- 각 항목에 '어떤 잘못된 구현이 이 테스트에서 FAIL해야 하는가?'를 먼저 적는다. 정상 경로만 아니라 해당 과제의 실패·동시성·복구·비정상 입력을 선정한다.
- 요구사항이 범위 밖으로 승인되었으면 `OUT OF SCOPE (승인 근거)`로 표시하고 필수 Must를 임의로 제외하지 않는다.

### 3) 테스트의 효력 확인 — RED/GREEN 구분
- 구현 중 기록된 **사전 실패(RED) → 최소 수정 → 통과(GREEN)** 증거가 있다면 원인과 명령을 점검한다. 원래의 실패가 단순 오타/환경 오류였으면 유효한 RED로 세지 않는다.
- RED 없이 완성 후 작성한 테스트를 'TDD 완료'라고 부르지 않는다. 대신 **반례 테스트**를 추가하거나 기존 테스트가 결함을 발견할 수 있는지 Assertions·경계값·실제 실행 경로를 확인한다.
- 가능하고 안전할 때만 격리된 임시 복사본에서 수정 전 코드/통제된 결함 주입으로 테스트가 실제 FAIL하는지 확인한다. 사용자 작업물을 파괴적으로 되돌리거나 운영 서비스를 고의로 중단하지 않는다. 수행하지 못하면 'RED 미확인'으로 기록한다.
- Mock, Fake, In-memory, Stub 사용 여부를 표시하고 **검증 경계**를 분리한다. 예: 내부 결제 시도 멱등성 PASS는 PG의 실제 중복 청구 방지 PASS가 아니다.

### 4) 실제 실행 및 품질 속성 확인
- 위험 높은 테스트를 먼저 실행한 뒤, 가능하면 **전체 테스트 → 빌드 → 린트/타입체크**를 각각 수행한다. 명령별 실행 환경, 결과/실패·스킵 수, 출력을 기록한다. 하나의 성공을 다른 검사의 성공으로 대체하지 않는다.
- API/상태/DB: 동시 요청, 중복 호출, 상태 전이 위반, 타임아웃, 저장 실패·재시도·복구, 기존 데이터 회귀 중 해당하는 것을 **입력·예상·실제**로 검증한다.
- UI: 해당될 때 제공된 내장 Browser에서 실제 버튼·입력·이동·오류 표시를 확인한다. Browser 접근 불가면 `NOT TESTED`.
- 데이터/AI: 원자료/분할/누수·Baseline·평가 지표·재현 명령·결과 파일을 검사한다. 측정값은 같은 설정에서 비교하고 실험하지 않은 개선을 주장하지 않는다.
- QAS 성능·확장성: 부하 수준, 동시 수, 데이터 규모, 환경, 측정 도구, 실제 p95/처리량 등 **측정한 지표만** 기록한다. 목표가 미정이면 `TARGET TBD`: 측정 자체는 가능하나 요구 충족 `PASS`는 불가하다.
- QAS 보안·가용성·사용성·변경 용이성: 승인된 시나리오와 해당 검증 방법이 있는 항목만 결과를 판정한다. 검사하지 않은 속성을 자동 PASS로 채우지 않는다.

### 5) 코드 변경 리뷰 — 독립 관점
- README·SPEC·ARCHITECTURE를 기준으로 변경 파일과 핵심 실행 경로를 다시 읽는다. 코드가 원래 요구사항·상태 불변조건·모듈 계약·Tactic을 위반하지 않는지 확인한다.
- **Critical**(Must/Hard 조건 위반, 중복 결제·데이터 손실·보안 위험) / **Important**(핵심 기능 오류·중요한 테스트 공백) / **Minor**(핵심 목적에 영향 작은 개선)로 분류하고 파일·라인·재현 조건·영향을 명시한다.
- 허용된 독립 리뷰 도구/서브에이전트를 사용할 수 있으면 사람이 승인한 경우에만 활용한다. 없으면 **동일 세션의 반대 관점(Self adversarial review)**으로 확인하고 독립 리뷰라고 주장하지 않는다. 구현 모델이 바뀌었다고 독립 검증이 보장되는 것은 아니다.

### 6) FAIL 발견 시 수정·재검증 루프
- 재현 입력·기대·관측 차이 → 원인과 최소 수정 제안 → **사람의 수정 승인** → 수정 실행(승인된 작업 범위만) → 해당 테스트 재실행 → 영향받은 회귀·빌드 재실행 순서.
- 수정 후 이전 PASS는 해당 파일·의존 경로가 영향을 받았다면 **STALE**로 취급한다. 최종 보고 직전에 코드·테스트가 다시 변경됐는지 확인하고, 최신 코드에 대해 실행하지 않은 항목은 PASS를 철회한다.
- 시간/환경 제약으로 재검증하지 못하면 `NOT TESTED`와 남은 위험을 기록한다. 결함을 숨기고 '모두 완료'라고 하지 않는다.

### 7) 판정 및 제출 전 보고
- **PASS:** 현재 코드에서 해당 요구를 직접 검증하는 최신 실행 증거가 있다.
- **FAIL:** 실행 결과가 요구를 위반한다.
- **NOT TESTED:** 실행 불가, 증거 없음, 테스트 범위 부족, 최신 변경으로 증거 무효.
- **PARTIAL:** 일부 시나리오만 검증. PASS 집계에서 제외.
- **RISK ACCEPTED:** 사람이 미검증·잔여 위험을 이해하고 수용한 별도 결정. PASS가 아니며 필수 Must/Hard 조건 위반을 해소하지 않는다.
- **TARGET TBD / GAP:** 목표 미정 또는 요구→설계→테스트 추적 공백. 증거가 아닌 설명 표시.

`VERIFICATION.md`에 **테스트 명령, 관측된 결과/종료 코드, 변경 기준 시점, 적용 범위, Mock 한계, 결함 위치, QAS 측정 근거, 남은 위험**을 간결히 기록한다. 민감한 키·토큰·개인정보·과제 원문을 외부로 전송하지 않는다.

최종 메시지는 `검증한 범위 / Must·Hard NFR 미충족 / QAS 실측·TBD / Critical·Important / 재검증 필요 / 제출 전 사람 확인` 순서로 짧게 보고한다. **Must/Hard FAIL 또는 핵심 NOT TESTED가 남았다면 제출 준비 완료라고 주장하지 않는다. 제출 결정은 사람이 한다.**
